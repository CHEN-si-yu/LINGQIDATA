## Skill Prompt（可直接使用）

```
基于现有模型代码和报告，帮我设计和规划下一代的研究脚本。

## 背景
- 现有版本位于项目 Model/ 目录下
- 每个版本有 4 个核心文件: model.py, run.py, train.sh, analysis.ipynb
- model.py 包含所有核心逻辑: 参数解析、数据加载、归一化、损失函数、模型架构、LightningModule、训练入口
- run.py 是薄封装层，遍历 N 个季度调用 train()
- train.sh 是训练启动器
- analysis.ipynb 是独立分析脚本，记录了每个模型的回测结果。其中比较关键的指标包括 IC、top_return、Top 1 (个人, 不过滤涨停) 的 年化收益
- 数据路径由项目配置指定

## 要求
1. 首先阅读 reports/ 下的上一代分析报告，了解已有结论
2. 设计下一代研究策略报告，放在 reports/ 目录下
3. 第一个子版本为 Baseline，集成上一代的最优策略
4. 后续子版本在 Baseline 基础上进行单一变量对照实验
5. 每个子版本目录创建 4 个核心文件: model.py（主要修改）, run.py, train.sh, analysis.ipynb（后三个尽量不改）
6. **【强制】每个脚本生成/修改后，必须执行测试流程（见下文），通过后才能交付**
7. 验证完成后清理运行时产物，恢复正式数据路径
8. 将要求和提示词更新到 Skill 文档

## 【强制测试流程 — 每个脚本都必须执行】

测试用小样本数据: /root/autodl-fs/lingqiData/trainingdata/fac_sample.fea

具体步骤:
1. 将 model.py 中的数据路径改为样本数据路径
2. 将 max_epoch 改为 2, min_epoch 改为 1
3. 将 run.py 中的季度列表缩减为 1 个季度, n_folds 改为 1
4. 运行 train.sh，观察全程输出

## 实验设计原则
- 目标: 想尽一切办法提高模型的IC和Top 1收益
- 单次版本迭代需要设计出12个版本，尽可能的优化设计
- 修改集中在 model.py 中
- 回测框架: N 季度 × K-fold rolling window

## 文件模板结构
model.py 应包含以下组件（按顺序）:
1. imports
2. 环境配置 (线程数、精度等)
3. parse_args() - 命令行参数
4. 路径配置 (PROJECT_ROOT, root_path, fac_path, label_path 等)
5. params 类 - 全局配置与预加载数据
6. get_basic_name() - 模型命名
7. normed_data() - 数据归一化
8. collate_fn() - DataLoader 整理函数
9. DLDataset / DLDataModule - PyTorch Lightning 数据模块
10. 损失函数 (WPCC 及其缓存)
11. 时间衰减权重
12. LR 调度器类
13. PredictModel - MLP 网络结构
14. DLLitModule - LightningModule (training_step, validation_step, test_step, configure_optimizers, configure_callbacks)
15. train_single() - 单次训练执行
16. get_train_date_split() - 训练/验证/测试日期划分
17. train() - 主训练入口
```

##  事故复盘：V1.8 因子剪枝"空跑"事件

> **定性**：一个因 Hook 时机错误导致核心逻辑从未执行、但因"不报错不 NaN"而通过所有关卡、最终浪费 24 次完整训练的严重设计事故。

---

### 一、事故链（如何一步步漏过去的）

```
设计阶段                测试阶段                  全量回测                 分析阶段
   │                      │                         │                        │
   │ 梯度采集写在了         │ max_epoch=2 的          │ 6 季度 × 4 folds       │ "IC 差异 0%，这个方法
   │ on_train_epoch_end    │ 冒烟测试永远跑不到       │ = 24 次训练             │  无效，放弃吧"
   │ （.grad 已清除）       │ epoch 5 的剪枝触发点    │ 等价于 V1.0 × 24        │
   │                      │                         │                        │
   └─ 技术 Bug ──────────┘─ 测试盲区 ──────────────┘─ 算力全部白费 ────────┘─ 误导后续方向
```

**每一关都有机会拦截，每一关都漏了。**

---

### 二、三重根因（一句话总结）

| 层级 | 根因 | 本质 |
|:---:|------|------|
| **代码** | `on_train_epoch_end` 中访问 `.grad`（已被 `zero_grad()` 清除） | 不懂 Lightning Hook 生命周期 |
| **测试** | `max_epoch=2` 永远跑不到 epoch 5 的剪枝触发点，剪枝逻辑零覆盖 | 测试验证的是"不崩"，不是"正确" |
| **审查** | 结果与 Baseline 完全一致（0% 差异），无人警觉 | 把"空跑"当成了"方法无效" |

---

### 三、核心教训

> **教训 1：测试必须验证设计意图，而非仅验证"不报错"**
>
> 冒烟测试（2 epoch + sample 数据）只能捕获 import 错误 / CUDA OOM / shape 不匹配 / loss NaN。
> 它**完全无法**验证以下类型的设计是否生效：
> - 延迟触发的阶段策略（warmup、剪枝、curriculum、annealing）
> - 条件分支中只在特定 epoch 执行的逻辑
> - 依赖训练中间状态累积的机制（如 moving average、importance score）
>
> **原则：凡是有"在 epoch ≥ N 时触发"的逻辑，要么在测试时将 N 降为 1，要么将 max_epoch 设为 ≥ N+1。**

> **教训 2：静默失败是比 Crash 更危险的 Bug**
>
> Crash / NaN / OOM 立刻可见，会被立刻修复。
> 静默失败——代码正常跑完、loss 正常下降、checkpoint 正常保存——但核心设计从未执行。
> **唯一的检测手段是主动断言：代码里埋检查点，测试时验证检查点被触发。**

> **教训 3："与 Baseline 完全一致"是一个危险信号，不是中性结论**
>
> 任何指标差异 < 1% 的实验结果，必须执行以下复核而非直接接受：
> - 检查关键状态变量是否发生了预期的变化
> - 检查训练日志中是否有预期的阶段性输出
> - 如果设计了"从 epoch N 开始行为不同"，检查 loss/梯度曲线在 epoch N 是否有跳变

### 四、小样本测试强制验证清单（ 新增）

> **以下验证必须在 2-epoch sample 测试中完成，不通过不得交付。**

#### A. 通用验证（所有版本）

| # | 验证项 | 方法 | 不通过的表现 |
|:---:|------|------|------|
| A1 | 数据加载 | 确认 shape 匹配、无 NaN 爆炸 | 维度错误 / loss 为 NaN |
| A2 | 前向传播 | 确认 `forward()` 正常执行 | CUDA 错误 / 类型不匹配 |
| A3 | 反向传播 | 确认 loss 正常下降（不要求收敛） | loss 恒为常数 / 不下降 |
| A4 | 预测产出 | 确认 `model_res/` 下有 `.pkl` 文件生成 | 目录为空 / 文件缺失 |
| A5 | **结果差异化** | 确认输出的预测值与 Baseline（V1.0 或 V2.0）**md5 不一致** | md5 完全一致 → 代码可能根本没改到关键路径 |

#### B. 条件验证（存在以下设计时强制执行）

| 触发条件 | 必须执行的额外验证 | 方法 |
|---------|------|------|
| **存在 `if epoch >= N` 的延迟逻辑** |  确认逻辑在 epoch N 被触发 | 测试时将 N 临时降为 1，或 max_epoch 设为 ≥ N+1；检查日志中是否出现预期输出 |
| **存在梯度累积/统计（如 importance score）** |  确认累积值非零 | 在 `on_train_epoch_end` 中 `print` 累积值，或训练后 `assert 累积值.sum() > 0` |
| **存在条件 mask / 剪枝 / 开关** |  确认 mask 在触发后确实改变 | 训练后 `assert mask.sum() < input_dim` 或 `assert phase == 1` |
| **修改了损失函数** |  确认新 loss 值域合理 | 对比 Baseline loss 量级，差异应在预期范围内 |
| **修改了优化器 / LR 调度** |  确认 LR 曲线符合设计 | 检查 TensorBoard 或 `LearningRateMonitor` 日志 |
| **修改了数据归一化** |  确认归一化后数据量级合理 | `print` 均值/标准差，均值应接近 0，标准差应接近 1 |
| **涉及 `.grad` 的访问或修改** |  确认访问时 `.grad` 非 None | 在被访问处添加 `assert xxx.grad is not None, 'grad is None — Hook 时机可能错误'` |

#### C. 测试参数自适应规则

| 设计特征 | 默认测试值 | 修改为 |
|---------|:---:|:---:|
| 无延迟触发逻辑 | `max_epoch=2` | 不变 |
| 存在 `epoch >= N` 逻辑 | `max_epoch=2` | **`max_epoch = max(2, N+1)`** |
| 存在 `warmup_epochs=K` | `warmup_epochs=K` | 测试时 **临时改为 `warmup_epochs=1`**（验证逻辑能跑通即可） |
| 存在 `accumulate_grad_batches=M` | `M` | **`M=1`**（减少测试时间，梯度累积不是测试目标） |

### 五、防止未来同类事故的硬性规则

| # | 规则 | 违反后果 |
|:---:|------|------|
| **R1** | 在 `on_train_epoch_end` / `on_train_batch_end` 中访问 `.grad` → **Code Review 直接拒绝** | 梯度在 `zero_grad()` 后不可用 |

##  事故复盘：V5.0 复制粘贴"空跑"事件（2026-06-28）

> **定性**：V5.0 被设计为 V4.1 的"Baseline 复现"，但其 model.py 与 V4.1 逐字节相同、model_res 的 MD5 与 V4.1 完全一致（`484392fc4d3a5c34bb5812bd31e58dcb`）、346 天 × 1782 股预测相关系数 1.0000000000。这不是"完美复现"——这是文件级复制，是 V1.8 空跑事故在 V5.X 中的再现。**5 季度 × 4 folds = 20 次训练（如果真跑了）全部白费——相较于 V1.8 的 24 次训练浪费，这是同等严重程度的算力浪费事件。**

**V5.0 事故中，代码逐行相同 → 结果与 V4.1 完全一致 → 发现了，但被当作"成就"而非"事故"。**

### 五、核心教训（在 V1.8 教训基础上追加）

> **教训 4（V5.0 专属）：Baseline 如果是上一代冠军且不做任何修改，直接引用——不要重新训练**
>
> 如果一个新版本的 `.0` 基线被定义为"上一代冠军的完整配置、不做任何修改"，那么：
> - **不需要创建新目录**——在报告中直接写"Baseline = V4.1（Top 1 371.56%）"
> - **不需要跑任何训练**——引用已有结果即可
> - **如果确实需要独立复现验证稳定性**，把它当作一个**辅助验证实验**而非正式版本，只跑 1 个季度 + 1 个 fold，且在结果报告中明确标注"仅用于复现验证，非正式版本"
>
> **原则：VX.0 要么引入至少一项实质性改动（哪怕只是超参调整），要么不存在。**

> **教训 5（V1.8 教训 3 的强化）："与已有模型完全一致"永远是危险信号，绝不可能是正面发现**
>
> V1.8 事故后，教训 3 被写入 SKILL.md：
> > "与 Baseline 完全一致"是一个危险信号，不是中性结论
>
> V5.0 事故证明这个教训没有被真正内化——"完全一致"被重新包装成了"完美复现"的成就。
> **修订后的规则：任何新模型与任何已有模型的 model_res MD5 完全一致、或预测分数相关系数 > 0.9999 → 立即标记为事故，执行文件级比对，确认是否为复制。** 物理上不可能通过独立训练达到相关系数 1.0000000000——这一定是文件复制。

> **教训 6（V5.0 专属）：研究策略中的"不做任何修改"是设计层面的危险信号**
>
> 在 V5.X 研究策略中写入"V5.0 = V4.1 的完整配置（不做任何修改）"的那一刻，事故就已经被设计进去了。
> **研究策略审阅时，如果发现任何版本的计划修改量为 0，必须追问：这个版本存在的理由是什么？它会产生任何新信息吗？**

### 六、新增硬性规则（在 V1.8 五条规则基础上追加）

| # | 规则 | 违反后果 |
|:---:|------|------|
| **R6** | **VX.0 Baseline 必须包含至少一项实质性代码修改（参数/架构/逻辑），修改量 = 0 的 Baseline 直接拒绝创建** | 设计与已有模型无差别的 Baseline = 浪费计划 |
| **R7** | **如果 Baseline 确实是上一代冠军的精确复制且不需要修改，则：① 不创建新目录 ② 不运行训练 ③ 在报告中直接引用上一代结果** | 避免了 20 次训练的浪费 |
| **R8** | **小样本测试 A5（结果差异化）的参照对象必须包括所有已有版本的最优模型，不仅是对比 V1.0/V2.0。与任何已有模型 MD5 一致 → 事故** | 防止跨代复制事故 |
| **R9** | **结果分析阶段：任何新模型的 model_res MD5 与任何已有模型完全一致 → 立即停止分析，先执行文件级比对确认是否复制。相关系数 > 0.9999 → 同样是事故** | 不再将"完全一致"解读为"完美复现" |
| **R10** | **每个 VX.0 Baseline 的 model.py 必须输出一条唯一可搜索的日志，格式为 `[VX.0 Baseline] ...`，与任何已有版本的日志字符串不同** | 确保训练真的在跑 VX.0 的代码而非复制版本 |
| **R11** | **报告中的"完全一致"陈述必须附带物理可行性分析**：如果是独立训练，相关系数不可能 = 1.0000000000；如果报告声称独立训练完全复现了已有结果 → 立即人工复核 MD5 | 不把 bug 当 feature 写入正式报告 |
